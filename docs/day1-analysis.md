# День 1. Аналіз предметної області та архітектурні рішення

## 1. Постановка проблеми

Перед поїздкою мандрівник зазвичай вручну переглядає прогноз погоди на сайтах і сам вирішує, що взяти з собою. Через це:

- доводиться відкривати кілька сервісів і порівнювати дані на кожен день поїздки;
- прогноз важко перекласти в конкретні дії («+8 °C, 70 % ймовірність дощу» → «взяти парасольку та куртку»);

**Мета системи** - автоматизувати шлях «місто + дати → прогноз → готовий список речей» і доставити результат у зручний канал (вебсторінка та Telegram).

## 2. Цільова аудиторія та актори

| Актор | Опис | Канал взаємодії |
|---|---|---|
| Мандрівник (веб) | Планує поїздку з ПК або смартфона | Вебінтерфейс |
| Мандрівник (Telegram) | Хоче отримати список у месенджер | Telegram-бот |
| Open-Meteo | Зовнішній постачальник метеоданих | REST API |
| Telegram | Зовнішня платформа доставки повідомлень | Bot API |
| Адміністратор / розробник | Розгортає та моніторить сервіс | Docker, логи, `/health` |

## 3. Аналоги

| Рішення | Переваги | Недоліки щодо нашої задачі |
|---|---|---|
| Сайти й застосунки погоди (Sinoptik, AccuWeather) | Точний прогноз | Не дають рекомендацій, що взяти з собою |
| Застосунки-пакувальники (PackPoint тощо) | Генерують списки речей | Комерційні, часто англомовні, без Telegram |
| Ручний чек-ліст у нотатках | Гнучкий | Не враховує погоду |

**Наша ніша:** безкоштовний україномовний сервіс, який поєднує прогноз, правила формування списку та доставку в Telegram.

## 4. Варіанти використання (Use Cases)

1. **UC-1. Отримати план поїздки.** Користувач вводить місто та дати й бачить прогноз по днях і чек-лист.
2. **UC-2. Уточнити місто.** Система пропонує варіанти зі схожими назвами (наприклад, «Odesa, UA» чи «Odessa, US, Texas»).
3. **UC-3. Зберегти поїздку.** Поїздка отримує ідентифікатор, до неї можна повернутися пізніше.
4. **UC-4. Надіслати список у Telegram.** Користувач прив'язує чат через `/start` і отримує повідомлення.
5. **UC-5. План через бота.** Команда `/plan Львів 2026-10-20 2026-10-23` повертає відповідь прямо в чаті.

## 6. Нефункціональні вимоги

| ID | Категорія | Вимога |
|---|---|---|
| NFR-1 | Продуктивність | Відповідь `/plan` ≤ 2 с при «холодному» кеші, ≤ 200 мс при «гарячому» |
| NFR-2 | Надійність | Тайм-аут зовнішніх запитів 5 с, 2 повторні спроби; зрозуміле повідомлення про помилку (HTTP 502/504) |
| NFR-3 | Безпека | Секрети лише в змінних оточення; `.env` у `.gitignore`; перевірка `secret_token` для webhook; валідація вхідних даних через Pydantic |
| NFR-4 | Ліміти API | Кешування прогнозів на 1 год (Open-Meteo: до 10 000 запитів/добу для некомерційного використання) |
| NFR-5 | Переносимість | Запуск однією командою `docker compose up` |
| NFR-6 | Супроводжуваність | Шарувата архітектура (API → сервіси → клієнти), покриття тестами бізнес-логіки ≥ 70 % |
| NFR-7 | Зручність | Адаптивний інтерфейс (мобільний + десктоп), україномовний |

## 7. Обґрунтування вибору зовнішніх API

**Open-Meteo (API 1) замість OpenWeatherMap:**
- не потрібні реєстрація та API-ключ, тож розробка спрощується й немає ризику витоку ключа;
- безкоштовний прогноз на 16 днів (в OpenWeatherMap денний прогноз на 16 днів платний);
- має Geocoding API (пошук координат міста) від того самого постачальника;
- відповіді у JSON, параметри передаються через query string.

**Telegram Bot API (API 2):**
- безкоштовний, токен видається миттєво через @BotFather;
- підтримує webhook (зручно в хмарі) і long polling (зручно локально);
- аудиторія Telegram в Україні дуже велика, тож канал доставки природний для користувачів.

## 8. Чернетка правил чек-листа (Packing List Engine)

| Умова (за будь-який день поїздки) | Рекомендація |
|---|---|
| t° min < 0 °C | Зимова куртка, шапка, рукавиці, термобілизна |
| 0 ≤ t° min < 10 °C | Тепла куртка, светр |
| 10 ≤ t° max < 20 °C | Легка куртка / худі |
| t° max ≥ 25 °C | Легкий одяг, головний убір, пляшка для води |
| Ймовірність опадів ≥ 50 % або опади ≥ 1 мм | Парасолька, водонепромовне взуття |
| Снігопад (коди погоди 71-77, 85-86) | Зимове взуття з протектором |
| Вітер ≥ 10 м/с | Вітровка |
| UV-індекс ≥ 6 | Сонцезахисні окуляри, SPF 50 |
| Завжди | Документи, зарядний пристрій, аптечка |
| Поїздка > 3 днів | Додатковий комплект одягу, засоби гігієни |

## 10. Ключові архітектурні рішення

| Рішення | Альтернатива | Обґрунтування |
|---|---|---|
| Моноліт FastAPI (один контейнер) | Мікросервіси | Мала команда та 5 днів; модульність забезпечується внутрішніми шарами |
| SQLite у volume | PostgreSQL | Не потрібен окремий сервер БД; при потребі перехід через зміну `DATABASE_URL` (SQLAlchemy) |
| In-memory TTL-кеш | Redis | Один екземпляр сервісу; Redis можна додати в Docker Compose пізніше |
| Vanilla JS, роздача статики з FastAPI | React / Streamlit | Без етапу збірки; фронтенд і API в одному домені, тож CORS не потрібен |
| Webhook у хмарі, polling локально | Тільки polling | Webhook не тримає постійне з'єднання й краще підходить для безкоштовного хостингу |

## 11. Ризики та обмеження

| Ризик | Вплив | Захід |
|---|---|---|
| Недоступність Open-Meteo | Сервіс не може побудувати план | Кеш, повторні спроби, HTTP 503 з поясненням |
| Неоднозначні назви міст | Неправильний прогноз | Показ країни/регіону, вибір зі списку |
| Прогноз лише на 16 днів | Немає даних для далеких поїздок | Валідація дат і зрозуміле повідомлення користувачу |
| «Засинання» безкоштовного інстансу Render | Перша відповідь ~30 с | Попередження в README; пінг `/health` перед демо |
| Витік Bot Token | Компрометація бота | Токен лише в `.env` / секретах Render; при витоку відкликати через `/revoke` |
